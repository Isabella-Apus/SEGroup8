# 完整系统 HPA 正式实验报告

## 1. 实验目标与范围

本实验验证完整系统在负载升高和下降时能够自动扩容与缩容，并记录吞吐量、平均响应时间、P95 和错误率。HPA 必须绑定 Kubernetes Deployment，因此实际伸缩对象是承担共享系统计算的 `segroup8-backend`，不是 `secondhand-service`。请求路径为：

`frontend Service/Nginx -> shared compatibility backend -> MySQL`

混合负载覆盖首页、商品列表、分类、搜索热词和二手列表。实验提交为 `b622e6bbb0447d6823b50e7789e4777f7131eb9b`，运行环境是单节点 K3s。

## 2. 参数与方法

| 参数 | 正式值 |
|---|---:|
| CPU 目标 | 60% |
| 最小副本 | 2 |
| 最大副本 | 4 |
| 扩容策略 | 每 15 秒最多增加 2 个 Pod |
| 缩容稳定窗口 | 60 秒 |
| 固定/HPA 计量并发 | 5、10、20 |
| 每个计量阶段 | 30 秒 |
| 扩容触发阶段 | 120 秒 |

先运行固定 2 副本基准，再用相同入口、数据和压测器运行 HPA 2..4。两组都经过预热。`KEEP_OPTIMIZED_HPA=false`，所以脚本退出时恢复实验前状态。

## 3. 实验结果

副本时间线为 `2 -> 4（4 Ready）-> 2`，扩容、可用扩容和缩容均被观测到。六个正式计量窗口错误率全部为 0。

| 模式 | 并发 | 请求数 | 吞吐 req/s | 平均 ms | P95 ms | 错误率 |
|---|---:|---:|---:|---:|---:|---:|
| 固定 2 | 5 | 594 | 19.30 | 256.66 | 1205.14 | 0% |
| 固定 2 | 10 | 856 | 28.02 | 354.04 | 2093.66 | 0% |
| 固定 2 | 20 | 1175 | 37.90 | 520.12 | 3543.86 | 0% |
| HPA 2..4 | 5 | 748 | 24.41 | 202.24 | 1089.20 | 0% |
| HPA 2..4 | 10 | 896 | 29.27 | 338.39 | 1859.69 | 0% |
| HPA 2..4 | 20 | 1056 | 33.33 | 584.84 | 3235.61 | 0% |

同时验证了二手公开列表慢查询优化：5000 条临时数据下，执行计划从全表扫描和排序变为使用 `idx_secondhand_status_created`，本次 `EXPLAIN ANALYZE` 的执行时间由 2.880 ms 降至 0.464 ms，下降约 83.89%。该数据库结果是本环境的一次测量，不外推为其他环境的固定收益。

## 4. 为什么正式最小副本为 2

`minReplicas=1` 可以节省一个常驻 Pod，也更容易在课堂上观察从单副本开始扩容；代价是 Pod 重启、滚动更新和扩容冷启动期间没有冗余，突发流量到来后唯一实例更容易出现高延迟或短时不可用。正式建议使用 2 个预热副本。若只为演示采用 1，当前“每轮最多增加 2 个 Pod”的策略不保证出现 `1 -> 2 -> 4`，也可能出现 `1 -> 3 -> 4`。

## 5. 原始证据

- `summary.json`：正式指标和 HPA 判定；
- `replica-timeline.csv`：副本、Ready 副本和 CPU 时间线；
- `raw/*.json`：固定与 HPA 各阶段原始请求指标；
- `resource-snapshots.log`、`hpa-describe.txt`：资源和 HPA 状态；
- `database/`：索引前后执行计划与结构化结论；
- `environment/`：镜像、Deployment、Service、Ingress、探针和版本；
- `logs/`：后端、前端和 MySQL 的实验期日志；
- `NOT_RUN_OR_FAILURES.txt`：为空，表示脚本没有记录未执行项或失败项。

## 6. 复现

```bash
KEEP_OPTIMIZED_HPA=false \
bash scripts/experiments/cloud-native/reproduce_system_hpa_demo.sh
```
